# v0.6.0 — the maintenance hold now reaches both nodes

On 18 September an operator set the maintenance hold from the Home Assistant
dashboard, then rebooted the leader. The standby promoted anyway and both
instances ran for four hours.

Nothing was misconfigured. The hold was a file in one node's config directory,
and in the cold model only one node runs Home Assistant, so the dashboard the
operator reached was the only one that existed. `cluster-hold.sh` said "set it
on both nodes". There was no second dashboard to set it on.

This release makes the hold a property of the cluster rather than of a machine,
and fixes six further defects found while testing that change.

## What changed

| | |
|---|---|
| **The hold binds both nodes** | A key in the shared store alongside the local file. Either suspends failover, and setting or clearing from either node does both. The promoter reads it, which matters because on a cold standby the promoter is the only part of this system running. |
| **`BACKUP` now means stopped** | A node that rebooted under a hold came back with its state file reset on tmpfs and its container restored by `unless-stopped`, leaving no transition to act on. The promoter now reconciles it. Cold deployments only: on a warm standby a running Home Assistant is correct. |
| **The radios can report silence** | A Zigbee daemon died for nine days in front of a working sensor nobody had reason to look at. `radio_silent` raises a card and a push. It never fires on quiet alone, only on a radio that has never spoken or a watch matching nothing. |
| **The cold standby has a voice** | Its Home Assistant is stopped, so it never registered and the cluster read one member on a healthy pair and one on a broken one. Its promoter now reports the node and its clock, so member count and clock skew are real numbers. |
| **Messages say only what they know** | The promoter names the scope and origin of a hold. `cluster-hold.sh off` no longer claims to have cleared a node it cannot reach. |

Each defect is recorded in [`GOTCHAS.md`](../GOTCHAS.md) §29–§34 with its
evidence. One is worth naming here: **the reconcile above shipped as dead
code.** A misread dict shape made it evaluate false on every tick, every unit
test passed because the test's fake agreed with the bug, and it was found only
by creating the fault on real hardware.

## Upgrading

🚨 **The integration and the host bundle must be upgraded together.** HACS
updates the integration only. A 0.6.0 integration against a 0.5.x promoter
publishes the cluster-wide hold that no promoter reads, so the hold appears set
and binds nothing.

Nothing breaks if you forget. The bundle now carries the version it was
generated from, the promoter reports it, and the integration raises a repair
naming the node and the command to fix it. The hold switch says the same thing
instead of claiming a cluster-wide hold it cannot deliver. So the upgrade
completes itself the moment you run step 3, and tells you until you do.

1. Set the hold on both nodes by hand. The cluster-wide hold does not exist
   until the upgrade lands.
2. Update the integration through HACS, or copy
   `custom_components/cluster_state_sync/` into the config directory.
3. Regenerate the bundle from the wizard and re-run `install.sh` on the host.
4. Restart Home Assistant on the leader. The hold is what makes that safe.
5. Clear the hold.

There is no config-entry migration, so nothing is rewritten and downgrading
costs only the fixes.

**To enable the radio alert on an existing install**, tick `radio_silent` in the
options flow and add one watch pattern per radio. Entries already at the current
version do not gain it automatically. A single pattern covering several radios
does not work: the watch pools its patterns, so a live radio masks a dead one.

## What this does not do

A directly attached USB radio still cannot fail over, by construction. A
promoter that dies while its machine stays up still holds its radio claims; that
gap is now visible rather than silent, and the options for closing it are in
[ADR-009](../adr/ADR-009-radio-custody-failure-modes.md).

A Home-Assistant-only failure still takes about ten minutes to move the radios,
by design. Nothing here changes the failover budget.

## Verified on hardware

Both halves were proven on the reference pair on 22 September rather than in the
suite.

With a cluster-wide hold set, the leader was rebooted. The standby declined the
lease and stayed cold, which is the exact state in which it promoted during the
September incident. Separately, a second live Home Assistant was created
deliberately on the standby; the promoter stopped it four seconds after one
tick.
