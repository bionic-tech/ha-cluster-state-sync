# v0.4.1

One change, deliberately alone.

> [!CAUTION]
> **This release contains a P1 security fix.** It was cut as a no-hurry
> refactor; an adversarial review run before deploying it found that v0.4.0's
> command-injection fix was **incomplete**, and closing that is now the more
> important half of this release.

## 🚨 AR-0056 (P1) — v0.4.0's injection fix missed five fields

v0.4.0 introduced `validate_shell_safe` as a chokepoint, and its own docstring
explained why a chokepoint beats a hunt: *"the next person to add a site will
forget"*. It then validated a **hand-written list of thirteen fields** — which
is the same mistake one level up, and the list was already incomplete.

Five fields reached root-run shell unchecked, because they look like numbers
and nobody had typed them into the list: `redis_port`, `redis_db`,
`fileset_stale_after`, `iot_subnets` and `ha_uid`. Verified by execution, not
by reading:

```
--redis v:6379; touch /tmp/PWNED \      <- generated, and it ran
```

**The rule is now inverted: every config value is validated unless its key is
named as an exception, with a reason.** A field added tomorrow is checked by
default. Forgetting to think about one fails closed instead of open.

Four fields are exempt, each justified in code and asserted by tests:
`redis_password` (its single use wraps it in `shlex.quote` for a file the pull
sources — passwords legitimately contain `$` and quotes), `cluster_secret`
(never reaches a script; only its derived key ships, and a test greps every
artefact for a marker secret to keep that true), and the glob-bearing fields
that `bundle.py` never reads.

`iot_subnets` is validated by **shape** rather than exempted: it is a
comma-separated list where a space is ordinary, so rejecting spaces would
refuse a valid firewall and exempting it would leave nftables input unchecked.
Its elements must now be address characters only — an allowlist, which is
stricter than the generic rule rather than looser. An `nft` breakout
(`10.0.0.0/8 }; drop; #`) is refused along with the shell ones.

Both live configurations on the reference pair were checked against the new
rule before release: 29 and 24 keys now validated, where 13 were before, and
generated output for an ordinary configuration is byte-identical.

## `async_setup_entry` was 514 lines doing eleven unrelated jobs

Raised as **AR-0050** in adversarial review v3 and deliberately held back:
splitting the function that starts the thing which keeps a house running, in
the same release as a P1 security fix and a breaking promoter change, would
have destroyed the ability to say which change caused a regression.

v0.4.0 is deployed, drilled and stable, so this lands on its own.

| | before | after |
|---|---:|---:|
| `async_setup_entry` | 514 lines | **277 lines** |

Four self-contained blocks became four functions, each doing what it did
before, called from the same place in the same order:

| function | job |
|---|---|
| `_setup_recorder_snapshots` | the leader's consistent recorder copies |
| `_setup_fileset_replication` | publishing the go-bag |
| `_setup_statistics_replication` | publishing the history window |
| `_setup_degraded_alarm` | raising, or clearing, the degraded-go-bag repair |

**Extraction only.** No logic was rewritten, no order changed, no guard
altered. Each helper still sets its own `runtime[...]` slot, exactly as the
inline block did — including setting it to `None` when the feature is off,
which is the part a careless extraction drops.

## Two new tests, which are the actual point

A refactor of this function is safe only if something checks the contract it
could silently break. Nothing did.

* **`test_setup_fills_every_runtime_slot_the_platforms_read`** — asserts all
  ten `runtime` slots are filled after a real setup. The failure mode of a
  dropped slot is not an error: it is an entity reading a key that was never
  set, reporting `unknown` for ever.
* **`test_the_optional_feature_setups_stay_in_their_agreed_order`** — the
  go-bag must be published before the statistics that ride on its key and its
  secret, and the degraded alarm must come after both so it can describe what
  the swap installed. Nothing else in the suite notices if those swap places.

Both mutation-verified: dropping a slot and reordering two setups each fail
the relevant test.

The setup sequence was also compared operation-by-operation against the
pre-refactor function to confirm the spine is identical.

## Also fixed

### AR-0057 (P3) — switching replication on no longer accuses a correct setup

A missing follower status counts as stale, and on the pass that first enables
statistics no follower has had a window to fetch yet. The leader therefore
raised *"replication has stalled"* against a perfectly correct installation for
up to 90 minutes — on the one day its owner is least able to tell a new fault
from a new feature. It now waits until it has been publishing for longer than
the staleness window before believing silence.

### AR-0054 (P4) — the VirtualHere example hook no longer cries wolf

The drill recorded this as "reports FAILED while the radios transfer
correctly". Reading the hook properly showed it was not lying: it waited 15
seconds for the device nodes to disappear, they were gone by about 21, and the
peer claimed all five radios shortly after. The hook was right and its timeout
was too short.

`examples/hardware-custody/virtualhere-release.sh` now waits `RELEASE_WAIT`
(default 30s, overridable) and **exits 0** with a warning if the devices
linger, because a delayed peer is a delay and not a failed demotion. Reporting
`DEGRADED` on the happy path is exactly how a promotion-path signal gets
ignored.

**If you have copied this example**, your deployed copy is yours and is not
updated by an upgrade — raise its wait, or take the `exit 0`.

### AR-0058 (P3) — the installer now knows which machine it is on

A bundle belongs to **one node**: the container name, config path, node id and
peer are all specific to it. The existing container and config-path checks
caught a cross-install only where the two hosts happened to differ — and
anyone who followed a standard guide has `homeassistant` on both and the same
path, so nothing noticed.

It now asks the reliable inverse question. We may not know our own hostname —
the integration sees the *container's* — but we know the peer's, because the
operator typed it. If this machine answers to the peer's name, the script
refuses, **before** the container check, because "no container named
`homeassistant`" sends someone hunting a container problem when the real fault
is that they are on the other machine.

### AR-0059 (P3) — how to recover an install you lost half-way through

The bundle persists inside Home Assistant and `install.sh` has always been
safe to re-run. Neither was written down, so an operator whose SSH dropped and
whose clipboard was gone had nothing to go on.

`INSTALL.md` now opens with it: the command to fetch the bundle again, the
command to re-read the instructions themselves, that re-running the installer
is safe, and — the reassuring part — that **nothing is armed until the timers
are enabled**, which is the last thing the script does. An interrupted install
leaves files and no change in behaviour.

## Not done, and why

**`bundle.py` is still 3,200 lines.** It is the other half of AR-0050 and it
is the largest privileged surface in the project — it generates the shell that
runs as root on both hosts. It gets its own release, with its own drill,
rather than riding along with anything.

1,011 tests, ruff clean.
