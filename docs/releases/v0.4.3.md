## 🚨 AR-0065 (P1) — a promotion restored nothing

A promoted node resolved leadership and its flush loop published **its own**
state over the shared snapshot *before* the restore read it. Every entry then
carried its own `source_node`, the restore skipped all of them as `own-node`,
and **zero entities crossed** — which is the entire purpose of this
integration.

Measured on the reference pair, in both directions:

```
18:08:20.786  Leadership change -> LEADER, publishing state
18:08:20.787  snapshot written by node-b      <- overwrites the peer's
18:08:35.703  restore -> 28 own-node -> restored 0
```

**Deterministic on default settings.** `DEFAULT_SNAPSHOT_INTERVAL` is 5
seconds, so the flush wins the race on every installation. This was not a quirk
of one deployment's tuning.

Gating on leadership was never enough: a promoted node **is** the leader from
its first tick, because the host-side promoter takes the lease *before* it
starts Home Assistant, while the restore is deliberately deferred until
everything has started. `DATA_RESTORE_DONE` is what separates the two.

The gate opens in a `finally` — a restore that *raised* must still release the
flush — and by a 600-second fail-safe, because a gate that never opens starves
the standby entirely, which is worse than the bug.

**Proven on hardware, twice**, with a probe designed so the result could not be
misread: an `input_boolean` set ON at the leader whose stored value on the
standby was OFF, so "restored it" and "never changed it" could not be confused.
28 of 28 entities crossed each way. The gate held the flush for **56 seconds**
between leadership and restore.

### Why nothing caught it

This is AR-0040's shape a second time — and AR-0040's own write-up had already
named this exact behaviour as a knock-on, four months earlier. Fixing the other
half made the symptom disappear from the rehearsal and this half was never
closed.

The harness could not reproduce it because its Home Assistant is **too small**:

| | integration ready → restore runs |
|---|---|
| rehearsal | **48 ms** |
| production | **46 s** |

48 milliseconds is not one 5-second flush tick, so the restore won every time.
`tools/rehearsal/slow_start/` now defers `EVENT_HOMEASSISTANT_START` to where a
real instance puts it, and PHASE C forces the standby's value to **differ** —
without which "restored it" and "never changed it" are the same observation.
Verified both ways: the run passes with the gate and fails without it.

Three latent harness bugs fell out of making it realistic, each an assumption
that only held because the instance was unrealistically fast: `wait_up()` meant
"the port answers" rather than "has started", `logs()` tailed too few lines, and
PHASE C slept a fixed 15 seconds where it should wait for the publish.

## 🚨 AR-0066 (P1) — the failover alert fired on the recovery, not the emergency

Found by the drill run to prove AR-0065.

Config-entry options never reached the standby, so the alerting configured on
the leader could not fire there. Two failovers produced **one** notification —
the failback *to* the configured node. The promotion *to* the standby was
silent.

That is the worst possible shape: **the failover worth being told about is the
one where the leader dies and the standby takes over**, and the standby is by
construction the node without the settings. It announced the house coming home
and said nothing when it left.

`cluster-fileset-swap.sh` preserves each node's own entry on purpose — it
carries `node_id`, and a node promoted holding its peer's `node_id` renews the
*peer's* lease and both believe they lead. The reasoning is sound; the
bluntness was the bug.

So the rule is inverted rather than discarded. `CLUSTER_WIDE_FIELDS` is an
**allowlist** of six settings that describe the cluster rather than the machine
— both `notify_*` fields and the four replication-scope fields. Everything else
is still preserved locally **by default**, so a per-node setting added in a year
still cannot reintroduce split brain.

Verified on the promoted node: alerting **inherited**, `node_id` and
`ha_container` **local**.

## 🚨 AR-0068 (P1) — and then options changes failed the house over

Introduced and fixed the same day, by the fix immediately below.

`async_unload_entry` releases the cluster lease, and its comment has always
said *"unload covers reloads and reconfiguration"* — correct, and harmless
while nothing reloaded on an options change. Adding the update listener turned
every settings change on the leader into a real promotion.

Observed on the reference pair: two options submissions, and the house moved to
the standby. The operator was editing a field.

A `_RELOADING` marker now tells our own reload from a genuine removal. A
removal still releases the lease — a node that has stopped running the
integration must not make the peer wait out the full TTL.

**If you are running v0.4.3 from before this fix, take the maintenance hold
before touching any option.** The hold blocks the release, which is what
contained it on the reference pair.

## Options changes did nothing at all

No update listener was ever registered, so every options page in this
integration saved and then had no effect until the next restart. The connection
settings had it too — moving Valkey through the UI would have appeared to work
and not.

It matters most for alerting, where the failure is configuring your phone,
being told it saved, and the house being unable to reach you.

## Replication scope: configurable, and visible

`exclude_entities` was honoured by the filter and offered by **no screen at
all**. `include_domains` was reachable only by re-walking eleven wizard steps.

* **Options → Replication** covers all four settings.
* **`exclude_devices`** is new: a domain is the wrong unit for "not this
  thermostat". Stores device IDs, so renaming cannot silently re-enable it, and
  resolves through **both** registry events — resolve once at setup and a
  firmware update that adds an entity to an excluded device starts replicating
  it.
* **Two sensors and an admin panel card** publish the whole picture, including
  a warning when the two nodes disagree about what crosses.

## Automation on/off can now cross, honestly

Whether an automation is enabled is a decision you made, and it crossed
nowhere: a promoted node restored it from **its own** memory of whenever it
last ran.

Adding `automation` to the replicated domains now works — applied by calling
`automation.turn_on`/`turn_off` rather than by writing state. `AutomationEntity.is_on`
reads its own internal state, so a state write would have shown "off" while the
triggers stayed attached and the automation kept firing. Telling somebody
something is parked when it is running is worse than not replicating it.

Opt-in, not default: on a warm standby with `gate_automations` on, replicating
the gated "all off" would be disastrous.

## AR-0064 — the moment our own guidance needs

`GUIDE-ingress.md` says to claim a floating address only **after** Home
Assistant answers, and the promoter provided no such moment. `post-start.d/`
now does — and it waits for the instance to actually answer, because the
container exists in a second and Home Assistant takes the best part of a
minute. An address claimed in between returns 502 to a health check that then
stops looking.

Bounded at 180s, then the hooks run **either way** with `CLUSTER_SYNC_HA_READY`
set to `1` or `0`. Refusing would leave an unreachable node unreachable;
running blindly would claim an address for a black hole.

## AR-0060's half — an ingress probe

The infrastructure half stays yours. The sentence that was ours — *"none of the
cluster's probes look at whether anyone can reach it"* — is closed: an
optional, leader-only probe of a URL you configure, surfaced as a connectivity
sensor and a push condition.

401/403 count as **reachable**: an SSO challenge is the front door working.
404 and 502 do not. Redirects are not followed. Credentials are stripped from
the URL *and* from the HTTP client's own error strings.

> [!WARNING]
> **A green reading is not proof.** The request leaves the container inside
> your LAN, so split-horizon DNS can keep it green while the tunnel every
> external user depends on is down. Red is trustworthy; green is not; you still
> need a monitor outside the cluster.

## Smaller, and each one a silence

* **The pre-flight no longer disables hardware quietly.** It records what it
  switched off; the integration raises a repair and pushes. A node missing
  three radios looked exactly like a healthy one.
* **A restart and a failed promotion no longer read alike.** Both log "Restored
  NOTHING", but the explanatory clause said *"promoted with no state from its
  peer"* for both — so on a live cluster the two were indistinguishable on the
  one line that separates them. That wording cost hours during AR-0065.
* **AR-0055** — the panel's card heading was parsed out of the entity id, which
  a promoted node inherits from its peer. It named the machine that was *not*
  running, beside a correct LEADER tag. Now read from a locally-computed
  attribute.
* **`scripts/check_install.py`** refuses the install mistake that took the
  reference leader down: a backup copy left inside `custom_components/` is a
  complete integration and claims the same domain, and Home Assistant then
  imports neither, reporting only `No module named 'custom_components.'`.
* **The coverage floor was not the floor.** `coverage.py` rounds before
  comparing, so `fail_under = 92` enforced 91.5 — and pytest-cov printed
  `FAIL … not reached` while exiting 0. `precision = 2` now set.
