# v0.3.1

One feature, and three things learned while switching it on for real.

## Home Assistant can be healthy while every radio behind it is dead

The promotion probe asks Home Assistant whether it is alive. It can be, and
still have nothing to say: on this fleet a Zigbee daemon livelocked — 78% CPU,
no output for 32 minutes, its healthcheck reporting `healthy` — and the whole
house lost Zigbee with every signal the cluster watches staying green.

**New: `sensor.<node>_radio_silence`.** Seconds since the freshest of a set of
globbed entities was last heard from. Configure it in the wizard's *Entities
that prove a radio is receiving* field — here, `sensor.*_rssi_numeric`, 39
entities that update on every RFXtrx packet received. Empty by default, and off
when empty.

It reports **`unknown`, never `0`**, when it has no age to report, and the
`status` attribute says which of the two reasons applies: `no_matches` (the
globs match nothing — a configuration problem) or `no_reports` (**entities
matched, none has ever reported — the radio is deaf**). `no_reports` is the
loudest condition it can find and is deliberately not a large number, because
"never" has no age. **Alert on the attribute, not only on the value.**

It **does not gate promotion**, deliberately. Failing over because a radio died
would move the house onto a node whose radios may be no better.

This exists because the automation it replaces referenced
`sensor.rfxtrx_status` — an entity that has never existed in this
configuration. "RFXtrx reload on failure" had therefore never fired, for any
failure, ever. Protection believed in and never held.

## Four traps found by deploying it, not by testing it

**The wider glob masks what it watches.** `sensor.*_rssi_numeric` matches 39
entities, every one `rfxtrx`. Widening to `sensor.*_rssi` adds four more — a
WLED, two Sonoffs, a Konnected — and every one is a **Wi-Fi** RSSI. Freshest
wins, so a Wi-Fi chip reporting every 60 seconds pins the number near zero
through a completely dead RFXtrx. Watching more entities looks safer and is the
exact opposite. **One radio per watch list.**

**A radio repeating itself is not a silent radio.** `last_changed` does not move
when a sensor reports the same value again, so keying on it shows rising silence
for a radio in continuous, healthy reception. It keys on `last_reported`.

**It is blind for the first few minutes of an instance's life.** Home Assistant
writes every entity's state as it starts, so the sensor reads near-zero after a
restart whether or not a packet has arrived — measured at 0 s, 22 seconds after
a restart, on a node whose radios had sent nothing. Any alert threshold must be
longer than boot time.

**An `unknown` entity is not evidence of reception** — and counting one is the
bug this sensor shipped with. Home Assistant stamps `last_reported` on an
`unknown` state exactly as on a real reading, so the first version reported a
confident 60 s, 120 s, 191 s while all 37 watched entities sat at `unknown`.
It read exactly like a healthy radio when it was measuring nothing but Home
Assistant's own state writes. A sensor built to stop "green everywhere, and the
house did nothing" reproduced that failure on its first day, inside itself.

**And a fifth, which is a limitation rather than a bug:** "time since last
packet" needs a device that transmits *unprompted*. Where every watched entity
belongs to a switch or a remote, the sensor measures human activity, not radio
liveness — on this fleet the normal gap between packets reaches **9 hours**, so
a restart plus a quiet morning reads identically to a dead radio. Measure your
baseline's longest normal gap before setting any threshold. See §18a for how
much that cost when I did not.

All four are in GOTCHAS §18
and §18a, with the measurements from this fleet.
