# v0.3.5

History that survives a failover, a promotion that no longer waits ten minutes
to decide, and the first test in this project that asks whether an **upgrade**
breaks a running cluster rather than whether the code is correct.

> [!CAUTION]
> **This release contains a breaking change.** `cluster_promoter.py` and
> `cluster-promoter.sh` must be installed **together**. See below before you
> deploy.

## 🚨 Breaking changes

### The promoter's wrapper and program must ship as a pair

`cluster-promoter.sh` now passes `--base-grace`, `--ha-container` and
`--grace-reason-file`, and `cluster_promoter.py` gained the options to receive
them. Both halves are correct. Installed apart, they are not:

| combination | what happens |
|---|---|
| **old `cluster_promoter.py` + new `cluster-promoter.sh`** | `error: unrecognized arguments` → **exit 2 every ten seconds, on every node.** Neither node can take or renew the lease, so the cluster cannot fail over at all. |
| **new `cluster_promoter.py` + old `cluster-promoter.sh`** | Runs, but without `--ha-container` the grace cannot extend: a flat **120s** where there used to be 600s. Silent. |

**Upgrade procedure.** Stop the timer, install the whole bundle, start it —
never drop files in one at a time, because a `cp` racing a ten-second timer can
execute a half-written file:

```bash
sudo systemctl stop cluster-promoter.timer
sudo cp /path/to/bundle/* /etc/cluster-sync/
sudo systemctl start cluster-promoter.timer
```

This is now enforced by `tests/test_breaking_changes.py`, which fails if a
wrapper ever passes an argument its program does not accept.

### Failover timing changes on every node

The probe grace was a flat 600s. It is now **120s base**, extended toward 600s
only while the container is *demonstrably* restarting. A genuinely wedged Home
Assistant therefore demotes at about two minutes instead of ten.

Measured cold boots on the fleet this was built for: 24.0s and 62.9s to
`Home Assistant initialized`. 120s is roughly twice the slowest — the margin
the flat 600s was really buying, applied only where it is needed.

**If you relied on the old behaviour**, pass `--base-grace 600` and you have it
back exactly.

### The recorder hand-over runs for the first time

`cluster-fileset-swap.sh` has carried a recorder hand-over for several
versions, and it has never once executed, because nothing ever delivered a file
for it to install. With statistics replication switched on it runs on **every**
promotion: the promoted node's `home-assistant_v2.db` is renamed to
`home-assistant_v2.db.superseded` and the replicated store takes its place.

Nothing is deleted, and it only happens with Home Assistant stopped. Two bounds
worth knowing: `.superseded` is a **single slot**, so a second promotion
overwrites the first; and what it holds is either a stale standby recorder or a
previously-installed replica — never the leader's live history, which this code
never touches.

## Not breaking

Worth stating explicitly, because the answer was checked rather than assumed:

- **No entity was renamed or removed.** Three were added
  (`oversized_entities`, `recorder_snapshot_age`, `statistics_age`) plus a
  `statistics_seed` button. Existing dashboards, automations and history are
  untouched.
- **No new config key is required.** An entry written by v0.3.1 still sets up,
  and every new feature defaults to **off** — statistics replication included,
  because it needs a manual seed and switching itself on would raise a repair
  on a cluster whose owner changed nothing.
- **No Valkey key was renamed.** The two nodes upgrade one at a time; a renamed
  key would have them silently stop talking while both report healthy.

## Long-term statistics replicate

Turn it on and the years of energy and climate history behind the Energy
dashboard survive a failover. Raw `states` — the logbook, the last ten days of
detail — does not.

That split is not a compromise, it is what the measurements argue for. On a
3,595-entity estate:

| table | rows | growth |
|---|---:|---:|
| `statistics` — multi-year | 6,409,578 | **+5,535/day (~0.5 MB)** |
| `states` — 10-day raw | 3,977,092 | +324,517/day |

Block-replicating the whole database was measured at **4 GB a day** through
Valkey, to carry half a megabyte worth having. So only statistics cross, as
rows, through the same Valkey, the same sealed envelope and the same key as the
go-bag — no new transport, no new port, no node-to-node SSH, and identical
behaviour on Docker, Supervised and Home Assistant OS.

**One manual step, once.** Six and a half million existing rows cannot arrive at
half a megabyte a day, so press **Write statistics seed**, copy the file it
names to the standby, and it is adopted automatically after SQLite's own
integrity check passes. About 500 MB on an estate this size.

Verified end to end on a live pair with the standby cold and its container
stopped — including that the resulting database matches the leader's schema
exactly (13/13 tables, 20/20 indexes) and that Home Assistant's own recorder
reports it as current with no migration needed. See the
ADR-010 addendum.

## The upgrade test

`tests/test_breaking_changes.py` pins the five contracts a **deployed** node
depends on: the wrapper/program argument agreement, `MANAGED_FILENAMES`, the
config-entry keys, the Valkey key names, and entity identity.

Everything else in the suite asks whether the code is correct. This asks
whether installing it onto a running cluster would break it — and those turned
out not to be the same question. The promoter break above passed 913 tests.

## Also in this release

- **Storage-aware snapshot intervals.** `storage.py` works out what the config
  directory sits on from inside the container, with no host access, and warns
  in **GB written per day** rather than a predicted lifetime.
- **The promoter publishes a heartbeat**, so a stopped promoter stops being
  indistinguishable from a quiet one.
- **The attribute budget is enforced on write**, and says what it dropped.
- **The RTO figure was wrong and is corrected**: ~102s to *initialised*, not
  the 78.8s to HTTP 200 that was measured first.
- **ADR-009 corrected**: an HA-only failure *does* move the radios, about ten
  minutes late — not never.
- **The wizard asks about history first**, and filters the standby models to
  what the answer actually permits.
