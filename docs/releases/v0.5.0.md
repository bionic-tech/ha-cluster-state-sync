# v0.5.0

**A minor bump rather than a patch, because a migration rewrites what your
cluster replicates — and because the highest-value domain we carry was missing
from the default all along.**

> [!IMPORTANT]
> **`automation` is now replicated by default, and existing installs are
> migrated.** If your allowlist is exactly the old eleven-domain default, the
> upgrade adds `automation` to it. A customised allowlist is left alone. See
> *Upgrading* below.

## Upgrading

**Config entry version 1 → 2.** The migration runs automatically on first start
and is deliberately narrow:

| your allowlist | what happens |
|---|---|
| exactly the old default (11 domains) | `automation` is added — you accepted a default that was wrong |
| anything else | untouched, and version-stamped |
| not set at all | nothing to do; setup already falls back to the constant |

A customised list is a decision somebody made, and a migration does not overrule
decisions.

**No host-side artefacts changed.** Unlike v0.4.3, the bundle does not need
regenerating — the integration alone is enough.

**No breaking changes.** None of the contracts in
`tests/test_breaking_changes.py` moved.

## 🚨 `automation` was never in the default allowlist

It should have been from the start. It is the only replicated domain applied by
**calling a service** (`RESTORE_BY_SERVICE`) rather than by writing state — so
it is the only one whose restore actually takes effect instead of being
corrected by the next device poll.

Adding it to the constant fixes every install that never wrote an explicit
allowlist, because setup falls back to the constant. Installs where the wizard
wrote the defaults out — most of them — need the migration above.

## 🚨 The restore was overriding `initial_state`

`initial_state` is Home Assistant's documented way of saying *"force this
automation on or off at every startup, regardless of what was restored."* HA
applies it in `async_added_to_hass`, where it deliberately beats
`async_get_last_state()`.

Our restore runs later — on `EVENT_HOMEASSISTANT_START` — and applies
automations by calling a service. **A command lands after a pin, so we won, and
we should not have.** An operator who wrote `initial_state: false` opted that
automation out of restore, and every promotion put it back.

Found on an estate where an automation pinned off — because the hardware it
commands is not wired yet — would have been re-armed by any promotion following
a single manual toggle.

The restore now skips any automation whose config pins its startup state, in
**both** directions, and counts the skip in its summary so it is visible rather
than silent:

```
Restored 152 entities from snapshot (skipped: … 1 initial_state-pinned)
```

⚠️ Honouring it required reading Home Assistant's private `_initial_state`. That
is a deliberate exception to this project's public-APIs-only rule, taken because
HA exposes `initial_state` on no public API at all — not a property, not in
`extra_state_attributes`. A test pins that the attribute exists on the tested HA
version, so an HA bump that moves it fails CI loudly; if it ever moves
undetected, the guard returns `False` and behaviour reverts to what it was.

## The domain picker now tells you what not to tick

Selecting domains offered a bare alphabetical list. Every option looked equally
reasonable, so the honest reading was *"tick everything you care about"* — which
is exactly wrong, and expensive, because the flush writes the **full map**
whenever anything in scope changes. One churning domain turns an idle cluster
into a permanent write loop.

Each option now carries a verdict, the reason, and **your own entity count**:

```
input_boolean (13) — replicate: may be guarding an automation — losing it acts
device_tracker (1436) — not needed: your trackers report position again at once
media_player (58) — cosmetic: the player reports what it is doing
```

Recommended domains sort to the top. `docs/GUIDE-choosing-domains.md` carries the
worked scenarios, led by the case that overrides all the others: a toggle whose
only job is to stop an automation acting. Lose one of those in a failover and the
automation shuts down the appliance it was told to leave alone — with nothing
logged, behind a promotion that reports success.

It also documents the edge cases where the usual answer flips: `utility_meter`
and friends accumulate and *are* Home Assistant's; a `manual` alarm panel has no
storage of its own where Alarmo does; presence transitions can fire after a
promotion even though the boot restore cannot.

## Multi-select actually multi-selects

Choosing eleven domains took eleven separate menu round-trips. The cause was not
the selector's `mode` — it was `custom_value`, which makes Home Assistant render
a multi-select as a type-to-add chip box whatever the mode says.

Both domain pickers are now tick boxes. Two fileset pickers that *declared* tick
boxes while delivering chip boxes now declare what they actually are. An AST test
enforces all three rules across the flow so it cannot drift back.

`notify_services` deliberately stays a chip box: you configure alerting before
the phone pairs, so the service you need to name does not exist yet.

## The unreplicated-references sensor was always wrong, and amber

It reported `12` on the estate it was written for, six days after the fix it was
measuring had landed — and all twelve were verified present on the standby.

It tested referenced paths against a fixed floor of directories. That floor is
not the answer: the fileset also walks the configuration's `!include`s and
carries everything it finds, which *is* the fix made for the incident the
sensor's own docstring describes. Every path it flagged was already in the
go-bag.

**An amber warning that is always wrong is worse than no warning, because it
teaches an operator to ignore the colour.** It now counts what genuinely cannot
travel however hard the go-bag follows includes: a reference reaching outside the
config directory, one pointing at an absent file, and one the scanner could not
read.

## Operational: a leader-side restart is a failover

Not a code change — a documented trap, learned expensively during this release's
own deployment. `docs/GOTCHAS.md` §28.

```
16:27:14  docker restart homeassistant   (on the leader)
16:27:24  promoter tick — cannot reach HA — releases the lease, drops 4 radios
16:27:27  the restart command returns.  Three seconds too late.
```

The promoter probes Home Assistant every 10 seconds and demotes when it cannot
reach it. That is the point of it, and it cannot tell "died" from "being
restarted on purpose".

🚨 **So the maintenance hold is not politeness before a leader-side restart — it
is the only thing between a deploy and a failover.** Proven both ways on
hardware: without it the cluster moved; with it the promoter logged *"maintenance
hold set — renewed the lease, taking no action"* on every tick and nothing
budged.

The failback path is documented too, including the ordering trap: `--adopt` the
demoted node **before** the leader releases, or neither node is eligible.
