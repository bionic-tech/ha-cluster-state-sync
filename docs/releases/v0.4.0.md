# v0.4.0

A security release, and the first one where the tests ask whether *upgrading*
breaks a running cluster rather than only whether the code is correct.

> [!CAUTION]
> **Read "Breaking changes" before deploying.** `cluster_promoter.py` and
> `cluster-promoter.sh` must be installed **together**, and failover timing
> changes on every node.

**Upgrading from v0.3.1?** This note is self-sufficient — v0.3.5 was cut and
superseded the same day and was never deployed anywhere. Everything in it is
repeated here.

---

## 🚨 Security

### AR-0043 (P1) — Command injection into root-run shell, from the wizard

Values typed into the configuration wizard were interpolated into the scripts
in `/etc/cluster-sync/`, which systemd runs **as root, every ten seconds, on
both hosts**, with no quoting and no validation. Verified by execution rather
than by reading:

```
CONTAINER="homeassistant"; touch ./PWNED; #"    → executed
--redis valkey.lan$(touch ./PWNED):6379         → executed
```

Reachable through `ha_container`, `redis_host`, `redis_username`,
`ha_config_path`, and — in the warm-standby firewall artefacts — `peer_host`
and `ha_container_ip`.

**The boundary crossed is Home Assistant admin → root on the host**, in a
project whose whole premise is that the host does not need touching. It was
rated P1 rather than P0 only because a human `sudo cp` sits between the wizard
and `/etc/cluster-sync/` — a blind `cp *` nobody inspects.

**Fixed** with a validation chokepoint, not forty quote sites: any value
carrying a shell metacharacter or a space is refused **before a single artefact
is rendered**, and a test asserts that check is the first statement in
`build_bundle`. A new interpolation site cannot reintroduce this by being
forgotten.

**What you will notice:** if any of those fields contains a space, a quote or a
character like `;`, `&`, `$` or a backtick, the wizard now refuses it with a
message naming the fields to check. Ordinary container names, paths and
hostnames are unaffected — generated output for a normal configuration is
byte-identical to v0.3.1's.

### AR-0044 (P2) — Stored XSS in the cluster panel

The panel built its entire view as a template string assigned to `innerHTML`
with no escaping. One of the values it rendered is
`sensor.<node>_cluster_leader`, which is read from the shared Valkey store and
**written by the other node** — and the node registry is not the sealed-blob
channel. Write access to Valkey, with no cluster secret at all, was enough to
put markup into a page running with an administrator's session. **Fixed.**

### AR-0045 (P3) — The standby's status channel is now sealed

The channel a stopped standby uses to report problems was plain JSON, and its
free text was rendered on the leader's repairs panel. Anyone with Valkey write
access could put chosen text in front of an operator at exactly the moment they
are anxious and looking for instructions. **Now sealed** under its own label.

### AR-0052 (P3) — The quiet failure, now written down

**If Valkey becomes unreachable, both Home Assistants keep running normally and
the cluster silently loses the ability to fail over.** No node can take or renew
the lease, so a real failure afterwards promotes nobody — and from the dashboard
that is indistinguishable from a healthy cluster. It was in the ADRs and nowhere
an operator would meet it. Now in the README's limitations and TROUBLESHOOTING,
naming `binary_sensor.<node>_backend` as the only signal that separates the two
states, and saying plainly that it deserves a notification rather than a card.

## 🚨 Breaking changes

### The promoter's wrapper and program must be installed together

`cluster-promoter.sh` now passes `--base-grace`, `--ha-container` and
`--grace-reason-file`; `cluster_promoter.py` gained the options to receive them.

| combination | what happens |
|---|---|
| **old `cluster_promoter.py` + new `cluster-promoter.sh`** | `error: unrecognized arguments` → **exit 2 every ten seconds, on every node.** Neither node can take or renew the lease, so the cluster cannot fail over at all |
| **new `cluster_promoter.py` + old `cluster-promoter.sh`** | Runs, but the grace cannot extend: a flat **120s** where there used to be 600s. Silent |

```bash
sudo systemctl stop cluster-promoter.timer
sudo cp /path/to/bundle/* /etc/cluster-sync/     # the WHOLE bundle
sudo systemctl start cluster-promoter.timer
```

Never drop files in one at a time — a `cp` racing a ten-second timer can execute
a half-written file. `tests/test_breaking_changes.py` now fails if a wrapper
ever passes an argument its program does not accept.

### Failover timing changes on every node

The probe grace was a flat 600s. It is now **120s base**, extending toward 600s
only while the container is *demonstrably* restarting.

> [!NOTE]
> **Corrected 2026-09-09, after a failover drill.** This section first said "a
> genuinely wedged Home Assistant demotes at about two minutes instead of ten".
> That was wrong, and the drill proved it: the grace is measured from the state
> file's mtime, which is written on a leadership **transition**. It is a
> *post-promotion boot window*, not a timer that runs when a failure happens. A
> node that promoted hours ago has no grace left and demotes on the first failed
> probe — **measured at 21 seconds**, fault to peer promoted, with fail-back in
> 14 seconds.
>
> So this change affects **only the window just after a node promotes**, where
> it decides how long that node renews without probing while its own Home
> Assistant boots. Steady-state failover time is unchanged, and was always much
> faster than this project's documentation claimed. See the
> ADR-009 addendum.

Measured cold boots on the reference fleet: 24.0s and 62.9s to
`Home Assistant initialized`. 120s is roughly twice the slowest — the margin the
flat value was really buying, applied only where the evidence supports it. The
ceiling is hard, so a crash loop still demotes.

**To keep the old behaviour:** pass `--base-grace 600`.

### The recorder hand-over runs for the first time

`cluster-fileset-swap.sh` has carried a recorder hand-over for several versions
and has never once executed, because nothing delivered a file for it. With
statistics replication on it runs on **every** promotion: the promoted node's
`home-assistant_v2.db` is renamed to `.superseded` and the replicated store
takes its place.

Nothing is deleted, and it only happens with Home Assistant provably stopped —
the swap refuses if the container is still running. Two bounds: `.superseded` is
a **single slot**, so a second promotion overwrites the first; and what it holds
is either a stale standby recorder or a previously-installed replica, never the
leader's live history, which this code never touches.

### Not breaking — checked rather than assumed

- **No entity was renamed or removed.** Four were added.
- **No new config key is required.** A v0.3.1 entry still sets up, and every new
  feature defaults **off** — statistics replication included, because it needs a
  manual seed and switching itself on would raise a repair on a cluster whose
  owner changed nothing.
- **No Valkey key was renamed.** Nodes upgrade one at a time; a renamed key
  would have them silently stop talking while both reported healthy.

## History that survives a failover

Long-term statistics now replicate. Turn it on and the years of energy and
climate data behind the Energy dashboard survive a failover. Raw `states` — the
logbook, the last ten days of detail — does not.

That split is what the measurements argue for. On a 3,595-entity estate:

| table | rows | growth |
|---|---:|---:|
| `statistics` — multi-year | 6,409,578 | **+5,535/day (~0.5 MB)** |
| `states` — 10-day raw | 3,977,092 | +324,517/day |

Block-replicating the whole database was measured at **4 GB a day** through
Valkey, to carry half a megabyte worth having. So only statistics cross, as
rows, through the same Valkey, the same sealed envelope and the same key as the
go-bag — no new transport, no new port, no node-to-node SSH, and identical
behaviour on Docker, Supervised and Home Assistant OS.

**One manual step, once.** Press **Write statistics seed**, copy the file it
names to the standby. About 500 MB here; adopted automatically after SQLite's
own integrity check passes, so running the copy and the pull at the same time is
safe.

Verified end to end on a live pair with the standby cold and its container
stopped, including that the resulting database matched the leader's schema
exactly (13/13 tables, 20/20 indexes) and that Home Assistant's own recorder
reported it as current with no migration needed.

### And it tells you when it stops

The status channel carries a TTL, which meant that when it expired the leader
deleted its warnings and **replication that had stopped looked exactly like
replication that was working**. That is the same shape as this project's
founding incident, in code written after that incident was catalogued.

Silence is now measured. Going quiet for three publish intervals raises a
repair, and the promoter heartbeat separates *"the standby is up and its
replication has stopped"* from *"the standby is switched off"* — different
causes, opposite fixes, so they get different messages.

## The upgrade test

`tests/test_breaking_changes.py` pins the five contracts a **deployed** node
depends on: wrapper/program argument agreement, `MANAGED_FILENAMES`, the
config-entry keys, the Valkey key names, and entity identity.

Everything else in the suite asks whether the code is correct. This asks whether
installing it onto a running cluster would break it — and those turned out not
to be the same question. The promoter break above passed 913 tests.

  drift test rather than hand-maintained.

  what this repository can fix from what Home Assistant pins.

## Deployment record — node-a / node-b, 2026-09-08

Deployed and verified on the reference pair the day it was cut.

| step | result |
|---|---|
| Maintenance hold, both nodes | Confirmed honoured: leader *"renewed the lease, taking no action"*, standby *"not holding the lease, taking no action"* |
| Integration → tiger1 | v0.3.1 → v0.4.0; Home Assistant initialised in **25.4s** |
| Bundle regenerated | On the host, from the live config entry, so no secret left the node |
| Bundle → both nodes | Whole bundle, promoter timer stopped for the copy |
| Promoter after upgrade | **exit 0 on both nodes** — new wrapper and new program together |
| Hold cleared | tiger1 MASTER, tiger2 BACKUP within 25s |
| Adaptive grace live | `--base-grace 120` on both wrappers, program default matching |
| Promoter heartbeats | Both nodes present in Valkey — first time this signal has been consumed |
| Statistics seed | 484 MB written, copied in **19s**, adopted: **6,411,310 rows, schema 53** |
| First window published | 202,815 rows, 1,035 statistics, 4.48 MB sealed, 1.8s |
| Sealed status round-trip | Standby's status opened on the leader with the cluster key: `state: ok, seeded: true` |
| Final state | All three timers active on both nodes, every unit exit 0, no repairs raised |

Two things went wrong during the deployment and are worth recording, because
both are traps for anyone following the same steps:

* **A `sudo cp $DIR/*` glob is expanded by the unprivileged shell**, which
  cannot read a root-owned `0750` bundle directory — so the copy silently
  matched nothing. Combined with `set -e` this left the promoter timer stopped.
  The hold made that safe rather than serious. Use `sudo bash -c '...'` so the
  glob expands as root.
* **The borrowed-container trick cannot regenerate a bundle.** `docker run` on
  the Home Assistant image has no `redis`, and importing the integration package
  pulls in `backend.py`. The standby's bundle was generated on the *leader*
  instead, overriding the four fields that differ between nodes — the cluster
  secret and Valkey credentials are shared by definition, so nothing secret had
  to travel.

## Failover drill — node-a / node-b, 2026-09-09

Run the morning after deployment. Fault injected by stopping Home Assistant on
the leader; the house moved to the standby and back.

| step | result |
|---|---|
| Fault → leader released the lease | **1 s** (probe failed, no grace remaining) |
| Go-bag swapped in on the peer | 4 s |
| **Recorder hand-over — first ever run in anger** | ✅ 485 MB statistics store installed as the recorder; the old 44 MB one preserved at `.superseded` |
| Radios claimed by the peer | 21 s from fault — both RFXtrx units and the ConBee |
| Peer serving HTTP 200 | ~60 s |
| Fail-back (peer HA stopped → original leader MASTER) | **14 s** |
| Statistics store rebuilt on the demoted node | ✅ **6,413,077 rows, from its own recorder, no manual re-seed** |
| Radios back on the original leader | ✅ all 5 devices |

Three findings, all recorded rather than smoothed over:

1. **The ~10-minute HA-only failover figure was wrong** and had been repeated
   across the README, ADR-009 and this note. Corrected above and in the
   ADR-009 addendum.
2. **The VirtualHere release hook reported `FAILED (rc 1)` while the radios
   transferred correctly.** A red status over a working function — the inverse
   of the usual trap, and still a status that cannot be trusted either way.
3. **On the promoted node, every cluster entity is named after the *other*
   node** (`sensor.cluster_sync_node-a_…` on node-b). The values are
   correct and the node's identity is correct; the entity *ids* come across in
   the replicated registry. Cosmetic, but `…_node-a_…_is_leader = on` on
   node-b is exactly the sort of thing that misleads at 3am.
