# v0.3.0

Everything here was found or proven on a live two-node fleet, not in a test rig.

## Radio failover works

USB radios delivered over USB-over-IP now follow the lease. The promoter gained
two hook directories — `pre-start.d/` on promotion, `post-stop.d/` on demotion —
and VirtualHere ships as a worked example under `examples/`, installed by nobody.
Your provider is your business; the promoter only supplies the moment.

**The ordering is load-bearing and tested:** hooks run *before the device
pre-flight*, not merely before `docker start`. A container's `/dev` is a snapshot
taken at start, and the pre-flight disables entries whose hardware is absent — so
claiming last means a promoted node disables the radios it just acquired.

Measured: ~40s from a handover request to a promoted node with working radios,
and **~17s for a crashed node's radios to become claimable elsewhere.**

**You must mount `/dev/serial` into the Home Assistant container**, or it cannot
resolve by-id paths that do not exist inside it — the devices sit on the host and
every open fails `Errno 2`.

## An operator surface

A **Cluster panel** appears in the sidebar by itself — nothing to paste, no entity
names to edit; entities are discovered, so it is right on any node id and any
number of nodes. Alongside it:

* **Maintenance hold** — suspends failover on a node. Restarting Home Assistant on
  the leader without it is a full, permanent failover. This is the fix, and it is
  now where the mistake gets made rather than in a host script.
* **Hand over to peer** — a deliberate switchover, leader-only. Previously this
  meant stopping Home Assistant on the leader, which *is* the accident.
* **Flush snapshot** and **acknowledge degraded** — services that existed and were
  unreachable.

Buttons are coloured by risk with a stated legend: safe, caution, and *moves the
house*. The integration also files its device under a **Cluster** area, and never
overrides an area you chose.

## Choose what fails over

`include_domains` has been readable since the first release and settable only by
hand-editing the config entry. It is now a wizard step. `light` and `switch` are
offered but never default — restoring one writes a state change, and a state
change is what automations trigger on.

## Compose-managed installs

The promoter can start Home Assistant with `docker compose up -d --no-deps
<service>`, with an optional `--profile`. One service, never the estate. `stop`
never `down`. `docker start` remains the default.

## Fixes that were real outages

* `docker stop` had Docker's default 10s grace; Home Assistant writes `.storage`
  during shutdown, so every demotion SIGKILLed it mid-write. Now `-t 120`.
* The D3 probe grace was shorter than a real Home Assistant boot, so a promoted
  node judged itself dead ~27s before it finished starting, released, and stopped
  its own container. Every time.
* The release hold-down was tuned to 180s and flapped the cluster; restored to
  900s, with `--adopt` as the escape hatch.
* The promoter released the lease and stopped Home Assistant **silently**. It now
  says why, and says why it is refusing to take a lease back.

## Known gaps

**Containers Home Assistant depends on do not fail over.** deCONZ, zigbee2mqtt,
Z-Wave JS, MQTT brokers: each is its own container with its own database, and none
is replicated. A promoted standby can hold a Zigbee stick and still have no Zigbee.
Run them off the failover pair, or accept they are unavailable while the standby
leads.

**Remote access does not follow the leader by itself** — see the ingress runbook.
