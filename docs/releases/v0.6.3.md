# v0.6.3 — two blocking calls on the event loop, and the harness that hid them

Both defects in this release were named by the HACS default-catalog review. The
listing itself was closed rather than merged, for reasons that are not defects
and have no remedy here (see below) — but the review read the code first, and
what it found was real.

## `storage.inspect_path` ran on the event loop, twice per setup

`_setup_recorder_snapshots` probed the recorder database's path to decide
whether snapshots were worth enabling. `storage.inspect_path` stats the config
directory and reads sysfs, and it was called directly from the coroutine.

It ran **twice**, which is the part worth recording: the second call was inside
the `_LOGGER.info` that reported the first one's result. A log line that
re-derives what it is logging is easy to read straight past, because the cost
is hidden in an argument.

Both call sites now share one `async_add_executor_job` probe.

## `StatisticsPublisher.async_publish` stat-ed the database every interval

The same shape, on a timer rather than at setup: a `Path.exists()` on the
recorder database inside the publish coroutine, on **every** interval for the
life of the process. Setup-time blocking is paid once; this was paid forever.

Now a `run_in_executor`, matching the idiom that file already used for
`_export`.

## This is the third instance, so it is a pattern

`backend.py:506` and `backend.connect()` were the first two. Three makes it a
property of this codebase rather than three incidents: **anything that touches
the filesystem during setup or on a timer needs an executor**, and review
should look for that by default rather than on suspicion.

## The tests assert on the thread, not the call count

A worker thread has no running event loop, so `get_running_loop()` raising
*is* the evidence that the call was handed off. Each fix has a test that fails
against the pre-fix source.

## 🚩 And that test nearly could not exist

Worth reading if you ever write a "did this run on the event loop?" assertion.

A `MagicMock` handed to `hass.async_add_executor_job` is invoked on
**`MainThread`**, while a plain function passed the same way reaches
`SyncWorker_0`. Measured both ways under
`pytest-homeassistant-custom-component` 0.13.340 against Home Assistant
2026.6.4. Plain `asyncio` `run_in_executor` does not behave this way, so the
cause is Home Assistant's own default executor; the exact mechanism is
unmeasured.

The consequence is that `patch(..., side_effect=...)` reports *"it ran on the
event loop"* against **correct** code. The probe has to be installed with
`new=`.

And the obvious repair is worse than the bug: deleting the thread assertion
makes the test pass, against both correct and incorrect code, leaving a test
that asserts nothing.

## Upgrading

Nothing to do. No config-entry migration, no change to the host bundle's
interface, and no change to failover behaviour, timings or the maintenance
hold.

**There is no 0.6.2.** A commit of that name was made and reverted before any
tag or release existed, so the number names a tree in history that was never
published. It is skipped rather than reused, on the same principle as 0.6.0:
a version should name one tree.

## What this does not do

It does not change what the integration does, only which thread it does two
things on.

**And do not go looking for the warnings that should have announced it.** Home
Assistant's `block_async_io` guards exactly eighteen functions: `open`, `glob`,
`iglob`, `walk`, `listdir`, `scandir`, `import_module`, `time.sleep`,
`putrequest`, five SSL certificate loaders, and `Path.open`, `read_text`,
`read_bytes`, `write_text`, `write_bytes`. **Neither `os.stat` nor
`Path.exists` is among them**, so neither of these two calls could ever have
been reported — in any configuration, however long it ran.

Measured on a node running the defective code: **zero** `Detected blocking
call` lines in 365,350 log lines. That zero was never evidence of anything.

⭐ An instrument's silence counts for nothing until you have checked that the
thing you are asking about is on its list. This is why the review found them
and running the software never would have.

## On the HACS default catalog

`hacs/default#12385` was closed, not merged. The catalog does not accept an
integration that writes state for entities owned by other integrations, nor one
that reads and rewrites another integration's stored credentials. Both of those
are what this integration is for, so there is no change request to satisfy and
nothing here attempts one.

**Installation by custom repository is unaffected**, and that is how this has
always been installed.
