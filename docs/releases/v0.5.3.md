# v0.5.3

**Verified against every Home Assistant release it claims to support, and now
says which ones.** No change to what the integration does.

`hacs.json` declares a minimum. That is a promise about every release above it,
and Home Assistant ships monthly — so the promise grew by one untested version a
month while the suite ran against exactly one pinned release.

| Home Assistant | Suite | Recorder schema |
|---|---|---|
| 2026.6.4 | 1379 passed | 53 |
| 2026.7.4 | 1379 passed | 53 |
| 2026.8.3 | 1379 passed | 53 |
| 2026.9.2 | 1379 passed | 53 |

The recorder schema is read directly at each, not inferred from the two ends.
That was the highest-risk item: this integration reads Home Assistant's recorder
database directly to replicate statistics, and a schema migration would have
broken it quietly rather than loudly.

## The one real break, and why nothing caught it

`scripts/ha_compat_check.py` confirms that the 21 Home Assistant symbols this
integration imports still exist. It passes against 2026.9.2. The suite did not.

**Home Assistant 2026.9 replaces `voluptuous` with `probatio`**, a drop-in that
installs itself *under the name `voluptuous`* when Home Assistant is imported.
So `import voluptuous` in that process is `probatio._vol_shim`, and
`cv.custom_serializer` now returns probatio's `_Unsupported` sentinel.

The old `voluptuous_serialize.convert()` does not recognise that sentinel and
does not raise. It **returns** it — so a caller expecting a list of form fields
gets a non-iterable object, and the failure appears several frames from the
cause. Nothing was renamed, nothing was removed, and no breaking-changes section
mentions it, because from Home Assistant's side nothing broke.

**No runtime effect on this integration.** It never imports that library, and in
Home Assistant's own process the swap is consistent. The failure was in the
tests that check every wizard schema can be rendered for the frontend — which
matters, because an unserialisable schema is a setup step the operator meets as
an error where a form should be. Those now work on both the old and new
mechanism.

## Keeping it true as releases ship

- **`scripts/ha_version_matrix.py`** derives the supported list from `hacs.json`
  and PyPI: the latest patch of every minor at or above the floor. Derived, not
  hardcoded, because a hardcoded matrix stops including the release that broke
  you. It respects the floor's own patch level and skips yanked releases.
- **`scripts/ha_matrix_check.py`** runs the suite against each of them locally,
  caching a virtualenv per version.
- A generated matrix in CI does the same on a schedule — **currently dormant**,
  because the cloud CI account has no credit. The local runner is what proved
  this release, run inside a `python:3.14` container on the standby node so a
  live cluster member needed no new packages and stayed BACKUP throughout.

🚨 **The runner refuses to start on an interpreter Home Assistant cannot use.**
Building the environment with a system `python3` (3.12) does not fail: pip walks
*backwards* to the newest release that interpreter can run. On one attempt that
meant Home Assistant 2025.1.4 — twenty months behind the pin — with the whole
suite green against it, proving nothing at all.

## Upgrading

Nothing to do. The pinned target stays 2026.6.4; this release is about proving
the range around it rather than moving it.
