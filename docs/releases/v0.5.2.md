# v0.5.2

**Two defects, both found by using the thing rather than testing it, and both
in the machinery that is supposed to tell you when something is wrong.**

> [!IMPORTANT]
> **No config entry migration, but host-side artefacts changed.**
> `cluster-promoter.service` gains two log settings and `cluster_promoter.py`
> learns to expire an automatic hold, so **regenerate the bundle and re-run
> `install.sh` on both nodes** — or drop the two lines into an
> existing unit by hand. The integration alone is not enough for that fix.

## 🚨 A reload re-announced everything that was still wrong

Every options change reloads the config entry, and a reload built an
`AlertRouter` with nothing recorded as active. So every condition that was
*still true* raised again — and pushed again.

Measured on the reference estate, 2026-09-11, over forty minutes:

```
3 ALERT raised: devices_disabled
1 ALERT raised: ingress_unreachable
```

Three identical *"Promoted without 1 device(s)"* notifications, from three
reloads. `devices_disabled` is true on **every** start while a device stays
disabled, so this was not an edge case — it was every restart, forever.

**An alert channel that repeats itself is one people stop reading, which costs
exactly the alert that matters.**

It cut the other way too, and more quietly:

- **No all-clear.** A fault that cleared after a reload sent nothing, because
  `async_clear` found no active condition to clear. Whoever was woken by the
  raise was never told it recovered.
- **An orphaned card.** `_dismiss` only runs from `async_clear`, so the
  persistent notification stayed on the repairs page. One raised at 09:36 was
  still sitting there twenty minutes after the fault was fixed. Persistent
  notifications stopped being entities in 2023, so nothing in the state machine
  shows a stuck one either.

The router's edge state — what is active, and each condition's flap window —
now survives a reload.

⚠️ **Deliberately in memory, and dropped on a real unload.** A genuine Home
Assistant restart *should* re-evaluate everything from scratch; it is only the
reload, an implementation detail of changing a setting, that must be invisible.

## The TLS context is no longer built on the event loop

Home Assistant reported this integration three times on every connect:

```
Detected blocking call to load_default_certs ... inside the event loop by
custom integration 'cluster_state_sync' at backend.py:506
```

`redis` builds its `SSLContext` lazily inside `RedisSSLContext.get()`, on
whichever thread first opens a connection — and that reads the system trust
store from disk. `redis` 6.4's `SSLConnection` accepts no pre-built context, so
it cannot simply be handed one.

What it does expose is `ConnectionPool.connection_class`. The context is now
built once in a worker thread, and the pool is pointed at a subclass that hands
every connection that finished object. Warming a single connection would have
fixed only the first, because each one builds its own `RedisSSLContext`.

🚨 **This reaches into another library's internals on the cluster's critical
connect path, so it fails open by design.** If `redis` reorganises, the correct
outcome is the warning coming back — never a cluster that cannot reach its
backend. A test asserts that a pool we do not understand, and a pool that raises
outright, both leave `connect()` working.

## A restart no longer looks like a dead node

A restart that Home Assistant initiates — the **Restart** button, the
`homeassistant.restart` service, or a `SIGHUP` — now holds failover for itself,
so the promoter does not read the gap as a dead node and move the house.

⚠️ **Read this before relying on it: a `docker restart` is NOT covered, and that
is the incident that prompted the work.**

Home Assistant maps `SIGTERM` and `SIGINT` — what `docker restart` and
`docker stop` send — to `exit_code 0`, which means *shutting down*. Only the
restart service and `SIGHUP` set `RESTART_EXIT_CODE`. That mapping is correct:
from inside, a `SIGTERM` genuinely is a shutdown, and the right response to a
shutdown is to release the lease immediately so the peer takes over rather than
waiting out the TTL.

So this closes the case where Home Assistant restarts *itself* — which is what
you do from a phone, and the one nobody remembers to set a hold for. **For a
host-side `docker restart`, the maintenance hold is still the answer**, exactly
as `GOTCHAS.md` §28 says.

The promoter cannot tell "died" from "being restarted on purpose" and should
not guess. Where Home Assistant *does* know, it can now say so. `async_stop` assigns
`exit_code` *before* firing `EVENT_HOMEASSISTANT_STOP`, so at that moment
`RESTART_EXIT_CODE` means "coming back" and `0` means "going away". On a restart
the integration writes a hold; on a genuine shutdown it does the opposite and
releases the lease immediately, exactly as before, because somebody stopping
Home Assistant deliberately wants the peer to take over now.

**The hold expires on its own after 300 seconds**, and the expiry is enforced by
the *promoter*, not the integration. If Home Assistant never comes back, the
thing that set the hold is gone and nothing inside it could ever clear it — a
cluster would sit held forever on a dead node, which is the failure the hold
exists to prevent, pointed the other way.

300 is not arbitrary:

| | |
|---|---|
| Slowest restart measured | 65 s — covered nearly five times |
| Promoter's probe grace | 600 s, anchored to the state file's mtime |
| A hold does **not** touch that file | so the grace clock runs *underneath* the hold |
| Therefore a crash mid-hold | still demotes at ~600 s, exactly as today |

That third row is the whole design, and it was verified by reading the promoter
rather than assumed — the assumption had been the opposite, which would have
made an automatic hold *add* to failover time instead of costing nothing.

⚠️ **Two things it deliberately does not do.** It never stamps an expiry onto a
hold a person set — theirs is indefinite, and quietly resuming failover during
their maintenance would be worse than anything this fixes. And **only the leader
holds**: a standby holding through its own restart would refuse a lease that came
free because the leader died in that window.

## The promoter was drowning its own journal

Reported by the owner while diagnosing a real outage: `cluster-promoter.service`
runs every 10 seconds and systemd narrates each invocation with three lines of
its own — `Starting`, `Deactivated successfully`, `Finished`. Measured on the
reference node:

```
15 lines a minute  ->  ~21,600 a day
```

None of them carry information. **The promoter is silent on a normal tick** —
every one of its thirteen messages is an exception or an event worth reading.

That is not untidiness. During the outage that morning the operator could not
find the DHCP and link events in the window at all, because the heartbeat had
buried them. A log nobody can search during an incident is doing harm, not
nothing.

The unit now sets `LogLevelMax=notice` and `SyslogLevel=notice`.

🚨 **Both, and the second is not optional.** `LogLevelMax` filters what systemd
writes *about* the unit — which is the heartbeat — but it also catches the
promoter's own output, which arrives on stderr at info. Measured:

| | heartbeat | promoter's messages |
|---|---|---|
| `LogLevelMax` alone | gone | **also gone (0)** |
| both together | gone | **intact (3)** |

One without the other gives you either a noisy journal or a cluster that has
stopped telling you anything.

**Deliberately not solved by slowing the timer.** Ten seconds against a
30-second lease TTL is three chances to renew before it lapses. Stretching it
trades failover latency for tidiness, and the tidiness was free.

## Also

Alerts now say so in the log — `ALERT raised`, `ALERT cleared`, and a
suppressed push naming the condition that was not ticked and that it is a
choice rather than a fault.

This shipped mid-cycle and immediately paid for itself twice: it proved
v0.5.1's ingress fix worked, and the *absence* of a matching `ALERT cleared`
is what exposed the reload defect above. An alerting system that cannot show
you it alerted is indistinguishable from one that is broken.

## The choice that matters most had no explanation

`leadership_source` — `always`, `entity` or `lease` — decides whether this node
writes to the shared snapshot at all. Its explanation was filed under two wizard
steps that do not contain the field, and the step that does contain it had none.

Home Assistant does not render help for a field that is not on the step, so the
text was not merely misplaced: **every operator who picked a leadership source
did it with nothing on screen**, while the guidance sat two steps away being
rejected by Home Assistant's own validator.

## Three things Home Assistant's validator had been trying to say

`hassfest` runs only on a CI runner, and this project's CI had been refusing to
start at all — a duplicate job key in the workflow file, which GitHub rejects
outright. Every run finished with zero jobs and no logs. With it running again,
three real errors surfaced:

- **`http` was used but declared nowhere.** The sidebar panel calls
  `hass.http`, so Home Assistant had no reason to set `http` up first. The
  panel's own error handling turned that into "no panel today" rather than
  anything you could diagnose. Declared as an `after_dependency`, deliberately:
  a hard dependency that fails means Home Assistant refuses to set this
  integration up at all, which is far worse than a missing icon.
- **No `CONFIG_SCHEMA`.** A `cluster_state_sync:` block in `configuration.yaml`
  was accepted and silently ignored. There is no YAML configuration for this
  integration and now it says so.
- **URLs inside translated strings.** Replaced with a placeholder, which is
  what lets them be translated at all.

## The blueprint pointed at a repository that does not exist

`source_url` is what lets Home Assistant offer you an updated blueprint. It
named an account that nothing is published from, and Home Assistant does not
report a `source_url` it cannot fetch — so "check for updates" would have found
nothing, quietly, forever.

## Release notes now reach the release page

The workflow built the path to this file from the git tag — `v0.5.2` — while
the notes were named without the `v`. The path never resolved, and the action
that publishes a release does not fail on a missing body: it publishes an empty
one. **v0.5.1 and v0.5.2 both went out with no notes at all**, assets attached,
every check green.

Notes now live in `docs/releases/` named for their tag, so the path is correct
by construction rather than by coincidence.

## You can now run what CI runs

The published repository ships its test suite, `./check` and its CI definition.
Until now `CONTRIBUTING.md` asked contributors to run all three and none of them
were here, so anyone taking the invitation seriously was blocked in their first
five minutes.

Also new: [a worked example install](../EXAMPLE-two-node-install.md) — two
machines and a Valkey through to a failover, every value filled in, ending in a
drill that plants a differing probe first. Without one, "restored your state"
and "did nothing at all" produce identical output.
