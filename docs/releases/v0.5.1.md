# v0.5.1

**Two fixes, both written the morning after a real 61-minute outage in which
every part of the monitoring worked and nobody was told.**

> [!IMPORTANT]
> **Config entry version 2 → 3.** If your alert conditions are exactly the old
> six-item default, the upgrade adds `ingress_unreachable`. A customised set is
> left alone. See *Upgrading*.

## What happened, because both fixes follow from it

On 2026-09-11 an unattended upgrade restarted `systemd-networkd` on the leader.
Its VLAN children came back; the parent interface's own IPv4 address did not.
The host stayed up, Home Assistant kept serving, and the cluster lease was
renewed every ten seconds over a surviving VLAN — while **nobody could reach the
house at its normal address for 61 minutes.**

The cluster behaved correctly throughout. The node genuinely was healthy, so the
standby correctly refused to promote: promoting would have been split-brain
against a live, serving peer.

What went wrong was everything downstream of *noticing*:

| | |
|---|---|
| Ingress probe detected it | **105 seconds** |
| Alert router raised a card | **~3 minutes** (3 failures × 60 s) |
| Push sent to the operator's phone | **never** |
| Cluster reaction | **none, and correctly so** |

## Upgrading

**`ingress_unreachable` is now in your alert conditions** if you never changed
them. That condition has been in `DEFAULT_NOTIFY_CONDITIONS` for some time, but a
default added to a constant does not reach entries that already exist — so every
install predating it has been quietly unable to tell you the front door is shut.

| your alert conditions | what happens |
|---|---|
| exactly the old six | `ingress_unreachable` added |
| anything else | untouched, version-stamped |

Same narrowness as v0.5.0's domain migration: an untouched default is an
accepted default; anything else is a decision, and a migration does not overrule
decisions.

🚨 **A v1 entry now collects both steps.** The v1→v2 code was
`if entry.version == 1`, which would have stamped an entry that skipped a release
straight to v3 and silently missed the alert conditions. Migration steps are now
cumulative (`if entry.version < N`) and a test asserts a v1 entry receives both.

**No host-side artefacts changed.** The bundle does not need regenerating.

## The ingress alert now says that nothing will act on it

The old message explained the fault well and stopped one sentence short of the
thing an operator most needs at 6am: **this does not resolve itself, and the
cluster will not move the house.**

The promoter probes Home Assistant at `127.0.0.1:8123`. A node that is healthy to
itself and unreachable to everyone else looks perfectly well from there, and
keeps the lease indefinitely. That is a deliberate design property — a localhost
probe is what stops a network blip causing a failover — but it means this
particular fault can persist for as long as nobody looks.

The alert now says so, and names the first thing to check, because it is the
least obvious:

> **NOTHING WILL FAIL OVER.** The promoter checks Home Assistant at 127.0.0.1, so
> a node that is healthy to itself and unreachable to you looks perfectly well,
> and keeps the lease indefinitely. This will not clear on its own.
>
> Check, in this order: this node's own IP address on its service interface (an
> interface can keep its link and lose its address, and its VLANs can survive
> while the parent does not), then DNS, then the reverse proxy or tunnel.

An interface that keeps its carrier and loses its address is not where anyone
looks first. It took sampling a Valkey `CLIENT LIST` and noticing the leader
connecting from a different subnet to find it.

## Still open, and honestly stated

⚠️ **The cluster still cannot see this class of fault.** Detection and
notification are fixed; reaction is not. An operator who wants this to trigger a
failover can point the promoter's `CLUSTER_SYNC_HA_URL` at the node's service
address rather than `127.0.0.1`, which turns an unreachable-but-healthy node into
a demotion. That trades away the blip protection, so it is not the default and is
not something this release changes for you.

Whether the cluster *should* act on "healthy to itself, invisible to users" is a
design question, not a bug. It is recorded in the internal backlog.
