# v0.6.1 — the pre-flight's remedy never worked, so it is gone

0.6.0 was published on 12 October and withdrawn the same day. Nothing in it
was broken that 0.5.3 did not already have, and its own test suite and CI were
green — but it carried a remedy that had never once taken effect, and once that
was understood there was no reason to leave it in front of anyone.

This release is that removal, plus two pieces of repository hygiene.

## The pre-flight no longer disables anything

`ha-device-preflight.py` runs before Home Assistant starts on a promoted node.
It finds config entries that point at serial hardware which is not attached,
and it used to disable them so Home Assistant could start without those entries
failing at setup.

It wrote `disabled_by = "integration"`. `ConfigEntryDisabler` has exactly one
member, `user`. Home Assistant rejected the value, so **the disable never
happened, in any release that shipped it.**

It is removed rather than corrected, on three measurements:

| | |
|---|---|
| **Nothing needed rescuing** | `setup_retry` does not give up. Measured 2 October: 91 retry lines, exponential backoff to a 600-second cap, 54 retries at the cap, 11.6 hours elapsed, and zero terminal failures. An entry whose hardware returns recovers on its next retry. |
| **It was the wrong layer** | A container's `/dev` is a snapshot taken when the container starts. A device attached at 08:34 does not exist inside a container started the previous evening, so Home Assistant reports `[Errno 2]` for a path the host opens perfectly. No amount of disabling config entries addresses that; restarting the container does. |
| **The costs are not comparable** | Leaving an entry enabled costs one log line per retry interval. Disabling it costs a blind that never opens, with no error anywhere. |

**The detection is kept, and it was always the valuable half.** The marker
naming which entries reference absent hardware is what let an operator
understand an eleven-hour outage in minutes. The script still writes it, still
reports what it found, and now says what will actually happen next — including
naming the `/dev` snapshot, which is the thing you have to act on.

Two consequences worth knowing. The script no longer edits
`core.config_entries`, so it no longer writes a backup beside it — relevant
because `.storage` is what fileset replication mirrors wholesale. And because
nothing is written, a second run on the same node reports the same entries
again rather than falling silent; the condition is still true, so it is still
reported.

## Repository hygiene

`.gitignore` now ships. `CONTRIBUTING.md` asks people to clone this repository
and run `./check`, which writes `__pycache__`, `.pytest_cache` and `.coverage`
into a tree that had nothing to ignore them.

CI now fetches tags. One test asserts that the release replay covers every tag
in the repository and deliberately refuses to pass when it can see none; a
default checkout fetches no tags, so it had been failing on every push. The
checkout was fixed rather than the assertion.

## Upgrading

Nothing to do beyond the usual. There is no config-entry migration, no change
to the host bundle's interface, and no change to failover behaviour, timings or
the maintenance hold.

**If you are coming from 0.5.x, read
[v0.6.0's note](v0.6.0.md) — it carries the upgrade steps, and the requirement
to upgrade the integration and the host bundle together still applies.** That
release is withdrawn, but its content is in this one.

**If you relied on the pre-flight disabling entries:** it never did. A node
that promoted with a radio missing has always come up with that entry enabled
and retrying, and that is what it will keep doing.

## What this does not do

A directly attached USB radio still cannot fail over, by construction. A
promoter that dies while its machine stays up still holds its radio claims
([ADR-009](../adr/ADR-009-radio-custody-failure-modes.md)).

And it does not make a hotplugged USB device visible to a running Home
Assistant. That is the container `/dev` snapshot described above, it is a
property of how the container is run rather than of this integration, and the
only fix from here is to restart the container.
