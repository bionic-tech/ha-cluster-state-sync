# v0.4.2

**Alerting.** Everything this integration knew was, until now, visible only to
somebody *looking* at Home Assistant.

> [!IMPORTANT]
> **This release is the deployment vehicle for v0.4.1 as well.** v0.4.1 was cut
> and never deployed, so a node running v0.4.0 receives both. Read
> [v0.4.1.md](v0.4.1.md) too — it contains a **P1 security fix**
> (AR-0056) and is the more urgent half of what you are installing.

## Upgrading from v0.4.0

**No breaking changes, in either release.** v0.4.0's promoter change was the
last one, and it is already deployed on any node running v0.4.0. Neither v0.4.1
nor v0.4.2 touches the five contracts in `tests/test_breaking_changes.py`:

| contract | v0.4.1 | v0.4.2 |
|---|---|---|
| wrapper ↔ program arguments | unchanged | unchanged |
| the set of files the bundle emits | unchanged | unchanged |
| an existing config entry still sets up | asserted | asserted |
| Valkey key names | unchanged | unchanged |
| entity keys | unchanged | unchanged |

So the ordinary upgrade applies: install the integration on both nodes, restart
Home Assistant on the standby first, then the leader under a maintenance hold.
The bundle does **not** need regenerating — nothing host-side changed in either
release.

The two new config keys are optional and defaulted. An entry written by v0.4.0
sets up untouched, and the wizard is not re-run.

## Why this exists

The gap was not a missing feature. It was a category error in what the project
believed "observable" meant.

This integration exposes eighteen diagnostic entities, a sidebar panel and five
repair cards. That is a good observability surface — for somebody at a screen.
The premise of the whole product is **the house keeps working while you are
away**, and every one of those surfaces requires you to be home and looking.

The failure this closes is the one the project keeps rediscovering in new
clothes: a thing that reports success by saying nothing (AR-0040). A standby
whose statistics replication has died raises a card that nobody sees for weeks.
A node promoted onto a degraded fileset raises an ERROR that waits for the next
time somebody opens Settings.

## What you get

Eight conditions can now reach a person:

| condition | default | why |
|---|---|---|
| **Failover** — the house moved to the other node | **push** | a 21-second failover is otherwise invisible |
| **Recovery** — a condition below cleared | **push** | an alarm that stops without a word is one you cannot trust |
| **Valkey unreachable** | **push** | the house runs; it can no longer **fail over** |
| **Promoted with an incomplete configuration** | **push** | decision D4 promotes anyway — this is the only thing that says so |
| Statistics: schema mismatch, gap, not seeded, stalled | card only | real, but they can wait until Saturday |

The line the defaults draw is deliberate: **push what changes whether the house
is protected right now.** An alarm that cries wolf at setup is one nobody
believes at 3am, which is the only time it matters.

### Two tiers, and you choose per condition

- **Persistent notification** — always, for every condition, to every
  administrator. No configuration, nothing to set up, nothing to get wrong.
- **Any `notify.` service** — the Home Assistant mobile app, Discord, Slack,
  Telegram, email. Home Assistant already holds those credentials; this
  integration never sees them and stores only the service name.

Unticking a condition silences the **push** only. The repair card and the
diagnostic entities are raised regardless, so nothing is ever hidden — you
simply are not interrupted.

### The wizard step is skippable, and skipping it still works

Submitting the new page untouched is a complete configuration: four conditions,
delivered to every admin inside Home Assistant. Opting *in* to a channel is the
choice on offer — not opting *out* of silence.

You may type a `notify.` service that does not exist yet (a phone you have not
paired). A name that never resolves costs an alert and one warning in the log.

## The hard part: not crying wolf

### An ordinary restart must not look like a failover

On the cold-standby model a promoted node **starts** Home Assistant — so its
first leadership resolution is always "I am the leader". So is the primary's,
every single time it is restarted for maintenance. In-memory edge detection
cannot tell those apart, and would push a failover alert on every restart.

The snapshot's `source_node` settles it: it names whoever last wrote the shared
state, it lives in Valkey so it survives our restart, and it is not us until we
write. **A node holding the lease over another node's snapshot has just taken
over.** A node whose own name is on the newest snapshot has merely restarted.

This reuses state that already existed. No new Valkey key, no extra round trip,
and specifically **not** the host's `/run/cluster-sync/vrrp-state`, which would
answer the same question and needs a host-side helper this project has
repeatedly refused to grow.

### The other three

- **Edge-triggered, never level-triggered.** The repair sites raise-or-clear on
  *every* coordinator pass by design. Notifying from them directly would push
  the same alert every thirty seconds, forever.
- **A flap is not a conversation.** A condition that oscillates interrupts once
  per five minutes; the card stays exact throughout. The truth is cheap, the
  interruption is not. The two *edges* get separate windows, though — a fault
  that clears inside five minutes still announces that it cleared, which is
  when the all-clear is worth most. And recoveries are limited per condition,
  so a flapping statistics gap cannot swallow the all-clear for a degraded
  fileset.
- **Acknowledging is not fixing.** `clear_degraded` dismisses the alarm without
  pushing an all-clear. Telling somebody their problem is solved when all that
  happened is that they pressed a button is how a channel stops being read.

### 🚨 And the boot race, which would have silenced the flagship alert

*"This node just took over"* is raised during **our** setup — and on a cold
standby, that is a Home Assistant which began booting seconds ago. The
`notify.` service the operator chose belongs to a different integration, which
may not have loaded yet.

The first implementation dispatched immediately. It found no such service,
logged a warning naming a service that was perfectly correct, and dropped the
one notification the entire feature exists to send — on the exact node, and at
the exact moment, that the feature was built for.

Pushes raised before `EVENT_HOMEASSISTANT_STARTED` are now **held and flushed**,
not dropped. Persistent notifications are never held: that component is core,
is up before we are, and its whole job is to still be there when you look.

Caught by writing the test before believing the code, and confirmed by mutation
— reverting the hold fails that test and nothing else.

## Replication scope: configurable, and finally visible

The second half of this release, and it began as a question: *what is not
replicated, and where do I change it?*

The answer was uncomfortable. **`exclude_entities` was honoured by the filter
and offered by no screen at all** — settable only by hand-editing the config
entry. `include_domains` was reachable only by re-walking the eleven-step
wizard through Reconfigure. And "what actually crosses?" was answerable only by
reading `_should_track` and evaluating a four-step precedence chain by hand.

### A new unit: exclude by device

A domain is the wrong unit for *"not this thermostat"*. `climate` is replicated
because a promoted node needs the setpoints — but one climate device might be a
guest annexe on its own schedule, a test unit, or the hardware wired to the node
that does **not** fail over. Excluding it entity-by-entity means listing all of
them and remembering to come back when a firmware update adds a ninth.

`exclude_devices` holds device registry IDs, not names, so renaming a device
cannot silently re-enable replication for it. It resolves to entity ids once
and refreshes when either registry changes.

> [!WARNING]
> That refresh is the load-bearing part. Resolve once at setup and never again,
> and a firmware update that adds an entity to an excluded device starts
> replicating it — the exclusion still looks right in the UI, every health check
> stays green, and the only symptom is data crossing that the operator asked to
> keep local. Both the entity **and** device registry events are watched: an
> integration adding a device and its entities together can fire only the latter.

Precedence: an excluded device beats the domain allowlist **and** an explicit
`include_entities` — someone who ticks "never cross" has said something more
specific and more recent. The leadership entity (AR-0038) is still refused above
everything.

### Options → Replication

| | |
|---|---|
| Domains that cross | offered from the domains this instance actually has |
| Also cross these entities | for a meter total a domain would not carry |
| **Never cross these entities** | previously reachable from nothing |
| **Never cross these devices** | new |

### Two new sensors, and an admin panel section

`replicated_domains` and `replication_exclusions` publish the whole picture as
attributes — which is what lets the panel render it with no new API, and what
keeps the filter, the sensors and the panel from ever disagreeing.

The panel's **Replication scope** card is admin-only: everything else on that
page is a health reading, but this enumerates entity and device ids, which is a
map of the house. It shows and links; it does not edit. The options flow
validates, writes and reloads — a second way to write the same settings would be
a second source of truth.

`not_replicated_domains` lists only domains **this instance actually runs**. A
list of every domain in Home Assistant would be noise; the useful question is
"what do I run that is not crossing?".

🚨 **And it flags disagreement.** If the two nodes' domain lists differ, the card
says so. The leader publishes what its config says; the standby restores what
its config allows — so a domain the standby has dropped is simply not restored
on promotion, while every health check on both nodes stays green. Nothing else
reports this.

### Why `sensor` and `binary_sensor` are not on the list

Asked during review, and now written into the step itself rather than left to be
rediscovered:

1. **Derived, not authoritative.** The integration re-reads the device on the new
   node within seconds, so a restored value is stale before anyone sees it.
2. **Restoring writes a state change, and automations trigger on state changes.**
   The same hazard as `light`/`switch`, over far more entities.
3. **Volume.** Measured on the reference estate: raw `states` churns ~324,000
   rows a day against ~5,500 for long-term statistics, and a single entity
   (`sensor.watchman_missing_entities`, 100,911 bytes) was 12% of one payload.

The exception is a value that genuinely cannot be re-derived — a utility meter
total, a manually-set counter. That is what "also cross these entities" is for,
one entity at a time.

### The two channels, stated plainly

A recurring confusion, now on the page itself:

| | carries | filtered by |
|---|---|---|
| **State snapshot** | live entity **values** | domain allowlist, then the include/exclude lists |
| **Fileset** | `.storage` wholesale, `custom_components`, `www`, `blueprints` | a deny-list |

Entity and device *settings* — enabled, hidden, area, renames, which entities a
device has — live in `.storage/core.entity_registry` and `core.device_registry`.
Neither is in the deny-list, so **your tracking configuration replicates in
full**; only the live readings are allowlisted. (`core.restore_state` is the
deliberate exception: it is Home Assistant's own restore, and letting it cross
would have it fight ours.)

## Changing it later

**Settings → Devices & services → Cluster State Sync → Configure** is now a
menu rather than one form: **Backend connection** and **Alerts**. Alerting is
the setting most likely to change long after installation — a new phone, a
Discord channel that moved, a statistics alert that turned out to matter after
all — and it was previously reachable only by deleting the entry.

> [!WARNING]
> Splitting that flow exposed a latent bug worth naming, because anyone
> maintaining a two-section options flow will meet it. `async_create_entry`
> **replaces** the options wholesale. With one section that was harmless. With
> two, saving the alerting page would have discarded every connection override
> — and the entry would have kept working on the values in `entry.data` until a
> restart pointed Valkey at an address that no longer served it. Both directions
> are now merged, and both directions are tested.

## Alerting can never break the cluster

A wrong service name, an expired push token, an integration that failed to
load: every dispatch is individually wrapped and degrades to a log line. One
dead service does not stop the others — the one that still works is the one the
operator is actually holding. A missing service is logged **once**, not once
per pass.

Eight tests exist only to assert that this module cannot take the cluster
down with it — including that the boot-held queue is bounded, and that an entry
unloaded mid-boot pushes nothing afterwards from a listener nobody owns.

## Tests

| | |
|---|---|
| new tests | **104** |
| suite | **1,142 passing**, 5 skipped |
| coverage | **92.31%** — the floor is 92, and now genuinely means 92 |

The load-bearing alerting tests are the negatives — that an ordinary restart is
silent, that a fresh cluster does not alarm at install, that a repeated poll
announces once, that an unticked condition still raises its card. An alarm that
fires wrongly is worse than no alarm, because it teaches the operator to swipe
the notification away unread, and the one they swipe away unread will be the
real failover.

### The coverage floor was already failing, and that mattered

`./check` enforces 92%. Measured on the commit this release branches from, it
was at **89.14%** and had been failing — the plain `pytest` most changes are
checked with does not apply the floor, so nobody had seen it.

Bringing it back to green was not a numbers exercise. The uncovered code was
uncovered for one structural reason: **both optional features default to off,
so every existing setup test took the branch where they do nothing.**

🚨 Statistics replication is *enabled in production*, on the reference pair,
holding 6.4 million rows. The code that starts it, the timer that runs it, and
the failure path that keeps it running after a bad window had been executed by
no test at all. That is AR-0040's shape once more: the tested path and the
running path were not the same path.

What is now covered, and was not:

| area | why it matters |
|---|---|
| Setting up with statistics and recorder snapshots **on** | the production configuration |
| The scheduled publish itself, on leader and follower | a follower publishing would ship its stale history over the leader's |
| A failed publish not ending the loop | otherwise one transient error silently stops replication for the life of the process |
| The seed button's leader guard (AR-0048) | pressing it on a standby sends the wrong history the wrong way |
| The seed button's press lock (AR-0048) | two presses, one `.tmp` path, last rename wins |
| Both switch handlers | one of them **deliberately causes a failover** |
| `RedisBackend`'s degrade-never-raise reads | including `read_cluster_view`, which v0.4.2's promotion detection reads |
| `renew_leadership` returning **False** on error | returning True would be split brain: both nodes leaders, radios claimed twice |

A clamp was found while writing these: a requested statistics interval below
five minutes is silently raised to five. Correct, and now pinned.

### 🚨 And the floor was not the floor

Two consecutive runs of the same tree disagreed about whether the build was
green. `coverage.py` rounds the total to `precision` digits **before** comparing
it to `fail_under`, and the default precision is 0 — so `fail_under = 92`
really enforced **91.5**. Worse, pytest-cov prints its FAIL line from an
*unrounded* comparison, so a run could print

```
FAIL Required test coverage of 92.0% not reached. Total coverage: 91.89%
  ✓ pytest + coverage floor
✓ all local gates passed
```

and exit 0. A gate that prints FAIL and passes is worse than no gate, because
it is a gate you stop reading. `precision = 2` is now set, and the floor means
what it says.

## Not done, and why

**`bundle.py` is still 3,200 lines** — the other half of AR-0050, and the
largest privileged surface in the project. It gets its own release and its own
drill.

**AR-0064: our own ingress guidance still has no hook point to run in.** The
promoter has `pre-start.d` and `post-stop.d` only; a VIP or a DNS update must
claim *after* Home Assistant answers, and there is nowhere to put that. The
guide documents the gap rather than pretending otherwise.

**The wider infrastructure guide** — Valkey placement, radios over IP, updates
and pinning, monitoring — is written next, now that the monitoring section has
something real to describe.
